    Database Migrations¶

    PostgreSQL schema is managed with Alembic. Models live in plugins/relational_db/postgres.py (Base.metadata); migration scripts live in migrations/versions/. The migration environment reads the owner database URL from config.settings (POSTGRES_OWNER_URL, or LAWBYAI_OWNER_PASSWORD and POSTGRES_*).

    Commands¶

    Run through uv (the project's package manager):

    Task Command
    Apply all pending migrations uv run alembic upgrade head
    Apply up to a specific revision uv run alembic upgrade <rev>
    Undo the last migration uv run alembic downgrade -1
    Undo to a specific revision uv run alembic downgrade <rev>
    Create a migration from model changes uv run alembic revision --autogenerate -m "describe change"
    Create an empty migration (manual SQL) uv run alembic revision -m "describe change"
    Show the current revision uv run alembic current
    Show migration history uv run alembic history
    Show heads (tip revisions) uv run alembic heads
    Stamp an existing DB as up-to-date (no SQL) uv run alembic stamp head

    Workflow¶

    1. Change the ORM models in plugins/relational_db/postgres.py.
    2. Generate a migration: uv run alembic revision --autogenerate -m "what changed".
    3. Review the generated file in migrations/versions/ — autogenerate can miss column-level changes.
    4. Apply it: uv run alembic upgrade head.

    Note: autogenerate compares against the live database, so run it against a schema that is at the latest revision (upgrade head first).

    Migrations in the data store¶

    The app does not apply migrations on startup. PostgreSQLStore.initialize() only reads the revision of the database. If the revision is not the head revision, it raises SchemaNotAtHeadError.

    Migrations run with the owner connection (POSTGRES_OWNER_URL, user lawbyai_owner). The app role (POSTGRES_URL, user lawbyai_app) cannot change the schema. RLS policies for users/tenants live in the migrations (ADR-0003).

    Seed the procedures¶

    Run order: first migrate, then seed. The seed needs the procedure tables at head.

    uv run alembic upgrade head
uv run python scripts/seed_db.py

    The seed reads data/procedures/*.yaml and connects as lawbyai_app (POSTGRES_URL). It imports each file as the admin principal system:seed. It checks all files first. If a file is invalid or two files share a slug, it writes nothing, names the file or files and exits with a non-zero code. It prints one line per file with the slug, the revision and whether it changed. A rerun is safe: identical content writes no new revision.

    Overlapping upgrade runs¶

    Each online run of alembic upgrade head takes a session-level advisory lock with the key 0x6C61775F6D6967 ("law_mig") before it reads alembic_version. When two runs overlap, the second run waits. It then sees head and applies nothing, so each migration runs once.

    The run tries pg_try_advisory_lock every 1 s until a deadline. The default deadline is 300 s. Set MIGRATION_LOCK_TIMEOUT_S to change it. The value must be a positive number. If the value is 0, negative or not a number, the run fails before it connects. The error names the variable.

    • If the first try fails, the run logs one line. The line gives the key and the deadline.
    • If the lock becomes free before the deadline, the run takes it at the next try. Then it applies only the missing revisions.
    • The last try runs at the deadline. If the operating system wakes the run a little late and the lock is free at that try, the run takes the lock and continues. The deadline limits the wait for a held lock only.
    • If a lock try fails at or after the deadline, the run fails with a timeout error. The timed-out run applies no revision and does not write alembic_version. Another run can still change it in that time.
    • The timeout error gives the key, the deadline in seconds and the pid of the backend that holds the lock. If that backend ended before the run read pg_locks, the error gives "unknown" as the pid.
    • After a timeout, the process exits with a non-zero code. The one-shot init service then fails, and the services that depend on it do not start.
    • If a poll query fails, for example because the connection is lost, the run raises the database error. The run does not report it as a timeout.
    • When a process dies, PostgreSQL ends its session and frees the lock.
    • Offline mode (--sql) takes no lock and does not read the deadline.

    Docker / test compose¶

    The init service runs alembic upgrade head with the owner connection, then runs the bootstrap program. Start it before the app services.

    The test service runs alembic upgrade head with the owner connection, then runs the tests. The tests truncate tables. Run them in a separate Compose project, so that they use their own volume and not the pgdata volume of your normal stack:

    docker compose -p law-by-ai-test --profile test -f docker/docker-compose.yml run --rm test
docker compose -p law-by-ai-test --profile test -f docker/docker-compose.yml down -v

    Existing local databases created before Alembic (tables created via create_all) usually hold only local test data. Prefer a fresh volume for them. create_all does not create the RLS policies of the initial migration, and the later revisions change those policies, so the upgrade stops without them.

    Adopt such a database only when it matches the initial migration in full: the tables, the users_isolation and tenants_isolation policies, and ENABLE and FORCE ROW LEVEL SECURITY on users and tenants. On such a volume lawbyai_owner does not exist yet. Do these steps in order:

    1. Make sure that the two policies exist and that RLS is enabled. Run this query with psql as the bootstrap superuser, on the app database:
    SELECT c.relname, c.relrowsecurity, c.relforcerowsecurity, p.polname
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_policy p
  ON p.polrelid = c.oid AND p.polname = c.relname || '_isolation'
WHERE n.nspname = 'public' AND c.relname IN ('tenants', 'users');

    The result must have two rows. In each row, relrowsecurity and relforcerowsecurity must be t, and polname must be tenants_isolation or users_isolation. If a row is missing, a flag is f or polname is empty, do not adopt the database. Use a fresh volume. 2. Stamp the initial revision with the bootstrap superuser connection. This creates the alembic_version table: POSTGRES_OWNER_URL=<superuser URL> uv run alembic stamp 4439761c5e40. 3. Upgrade to the revision before the RLS hardening, with the same connection. This creates the objects that the next step expects: POSTGRES_OWNER_URL=<superuser URL> uv run alembic upgrade 77985ac8fa22. 4. Do steps 1 and 2 of "Upgrade an old volume" below. They create the roles and give every object, alembic_version included, to lawbyai_owner. 5. Run uv run alembic upgrade head with the owner connection (step 3 below).

    Do not stamp head, because the later revisions would then never run.

    Upgrade an old volume¶

    The Postgres init script makes the database roles. It runs on a fresh volume only. An old volume has one role, the bootstrap superuser (POSTGRES_USER), and that role owns every object. The new migration stops on such a volume. Use this procedure to move an old volume to the new role model.

    The procedure makes three roles:

    • lawbyai_owner runs the migrations and owns every object.
    • lawbyai_app is the role that the app, the worker and the tests use. It owns nothing.
    • lawbyai_auth cannot log in. It owns the login lookup function only.

    You cannot use REASSIGN OWNED BY to change the owners. The old owner is the bootstrap superuser, and Postgres does not reassign objects that a superuser owns. The block changes the owner of each object one at a time.

    1. Set LAWBYAI_OWNER_PASSWORD and LAWBYAI_APP_PASSWORD in the shell. Use the values from the Docker env file. Do not write a password in the SQL.
    2. Run the block below with psql -v ON_ERROR_STOP=1 as the bootstrap superuser, on the app database. This option stops psql at the first error. psql reads the two passwords from env with \getenv.
    3. Run uv run alembic upgrade head with the owner URL. Set POSTGRES_OWNER_URL to a URL with the user lawbyai_owner and the owner password.
    -- Read the passwords from env, so they are not in the SQL text.
\getenv owner_password LAWBYAI_OWNER_PASSWORD
\getenv app_password LAWBYAI_APP_PASSWORD
-- Keep the statement text (with the password) out of the server log on error.
SET log_min_error_statement = panic;
SET log_statement = 'none';

BEGIN;

-- The same roles, attributes and grants as the init script.
CREATE ROLE lawbyai_owner
  LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE
  PASSWORD :'owner_password';

CREATE ROLE lawbyai_app
  LOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE
  PASSWORD :'app_password';

CREATE ROLE lawbyai_auth
  NOLOGIN NOSUPERUSER BYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE;

GRANT CREATE, USAGE ON SCHEMA public TO lawbyai_owner;
GRANT CREATE, USAGE ON SCHEMA public TO lawbyai_auth;
GRANT lawbyai_auth TO lawbyai_owner WITH INHERIT FALSE, SET TRUE;

-- Give each object to the owner role.
ALTER TABLE tenants OWNER TO lawbyai_owner;
ALTER TABLE users OWNER TO lawbyai_owner;
ALTER TABLE legal_document OWNER TO lawbyai_owner;
ALTER TABLE rejected_document OWNER TO lawbyai_owner;
ALTER TABLE alembic_version OWNER TO lawbyai_owner;
-- The sequence belongs to its table. Keep this line after the table line.
ALTER SEQUENCE rejected_document_id_seq OWNER TO lawbyai_owner;
ALTER FUNCTION users_bump_session_version() OWNER TO lawbyai_owner;

COMMIT;

    The block runs in one transaction. If a statement fails, no change stays. If the database has more objects that the superuser owns, change their owner in the same way before you run the migration.

    Last-admin trigger and the admin audit table¶

    Revision c4a91e7f2b58 adds trg_users_last_admin on users. It refuses a change that leaves a tenant with no active admin (SQLSTATE 23514, constraint name trg_users_last_admin). The owner lawbyai_owner can skip it for maintenance with SET LOCAL app.skip_last_admin_check = 'on'. The trigger ignores this setting for every other role.

    The same revision adds admin_action_audit, an append-only log. lawbyai_app has only SELECT and INSERT. The downgrade stops while the table holds rows.

    Row level security is forced on this table, so it binds lawbyai_owner too. Without app.current_tenant the owner sees no rows, and a plain export or DELETE does nothing. To purge, run one owner transaction in psql that lifts FORCE, exports to a client file, checks the export, deletes, and restores FORCE before it commits. \copy writes on the client. Server-side COPY ... TO needs pg_write_server_files, which the owner does not have.

    BEGIN;
ALTER TABLE public.admin_action_audit NO FORCE ROW LEVEL SECURITY;
\copy public.admin_action_audit TO 'audit.csv' CSV HEADER
-- Check audit.csv (row count and content) before you go on.
DELETE FROM public.admin_action_audit;
ALTER TABLE public.admin_action_audit FORCE ROW LEVEL SECURITY;
COMMIT;

    Then run the downgrade again.
