    ADR-0016: Registry and strategy design for the document fetcher¶

    Context¶

    The Document Fetcher agent gets legal documents from several sources. Each source has its own base URL and its own transport. Some sources offer a REST API. Some sources have only web pages. Some documents arrive as files in object storage. The documents come in many formats, and some are scans.

    The code needs a clear way to add a source, to choose a transport, and to read a format. ADR-0014 deprecated the plugin system, so the design must not bring it back. The project has one maintainer. The design must stay small, typed, and easy to review.

    The fetcher downloads data from remote hosts. A source URL can point to an internal host. A remote host can send a very large or very slow body. The design must limit these risks.

    OCR raises a privacy question. A scanned document has no text layer. A hosted OCR service reads the document content. That content then leaves the self-hosted deployment.

    Decision¶

    1. Strategy pattern for transport. A FetchStrategy Protocol defines the transport: list references, read metadata, read bytes. Three strategies implement it: REST API, Tavily, and MinIO bucket. A Protocol fits because the strategies share no state.
    2. One hardcoded class per legal source. Each source class declares its name, its base_url, and its strategy_name in code. The base_url must use HTTPS and must not contain credentials. The class returns raw bytes. It does not parse them.
    3. Decorator registry. A generic Registry[T] lives in a module that imports nothing from the project. A source registers itself with @SOURCES.register("name"). A strategy does the same with STRATEGIES. A new source needs no edit to a central list.
    4. The registered name equals the module file name.
    5. A duplicate name fails at import time.
    6. A validation hook checks each source class when it registers.
    7. Module-level instances. The registries (SOURCES, STRATEGIES) sit next to their base classes. They are plain module-level objects. They are not class-level singletons.
    8. Autoload. Each package imports its own modules with pkgutil, so the decorators run. The loader skips base and names that start with _. It fails if a module does not register its own file name.
    9. Format parsers. Parsers for each file format register in the same way. They turn raw bytes into text. They enforce limits on page count, archive size, compression ratio, nesting depth, and text length.
    10. OCR through OcrManager. All OCR goes through one OcrManager. It has one provider: Mistral Document AI. OCR is off by default. When OCR is off, an image or a scanned input raises a typed OcrDisabledError. It is an error, not a result. The system does not read the scan locally, and nothing leaves the host. The ocr/ package is a leaf package. It imports nothing from the other fetcher packages. A later ADR may add another provider (a local model or a gateway) without a change in the callers.
    11. No local folder strategy. The fetcher does not read paths from the local file system.
    12. REST mapping. A source registers a small mapper in a REST_MAPPERS registry, keyed by source name. The REST strategy stays generic. The mapper turns the payload into the fetch contracts. It can declare id safety, an id pattern, and alternative content paths.
    13. Tavily policy. Tavily uses map to list and extract to read. It does not use crawl. Each call has a cap on pages. An empty key is an error.
    14. MinIO and base_url. MinIO ignores the https:// rule on base_url. The endpoint, the bucket, and the credentials come from Settings. Only the path of base_url is the key prefix.
    15. Agent lifecycle. The agent keeps one strategy for each source. It has a close() method, and it works as a context manager. The caller uses close() to release the strategies.
    16. Tenant id. The agent validates tenant_id against [A-Za-z0-9_-]{1,64}. It rejects any other value.
    17. Network safety. The REST strategy resolves the host at request time. This applies to the first URL and to every redirect. It rejects the request unless all resolved addresses are global. Loopback, link-local, and private addresses fail this check. A source can opt out with allow_private_hosts. The connection is not pinned to the checked address. A host can change its address between the check and the connection (DNS rebinding). The project accepts this risk.
    18. Size and time limits. FETCH_MAX_BYTES limits the size of a fetched body for every strategy. A larger body raises ResponseTooLargeError. FETCH_TOTAL_TIMEOUT is a total deadline for reading a body. A slow body stops when the deadline ends. OCR_MAX_BYTES limits the input size for OCR.

    Privacy consequence¶

    When OCR is on, the document content goes to a third-party service outside the self-hosted deployment. This breaks the "no document content leaves the host" property that the stack has otherwise.

    • The operator must opt in. The default stays off.
    • The operator must check the legal basis for the transfer before enabling OCR. This includes personal data in the documents.
    • The setting must be visible to the operator in the configuration and in the UI.
    • Document content must not appear in logs, with OCR on or off.

    This ADR does not give legal certainty. The owner may need a legal review of the transfer before release.

    Relation to ADR-0014¶

    The registry is a direct, internal pattern for fetch sources. It is not the plugin system that ADR-0014 deprecated.

    • There is no YAML registration and no Protocol validation of backends.
    • PluginManager is unchanged. It gains no types.
    • The new code does not import core.plugins or plugins.
    • The fetcher does not import PostgreSQLStore. Persistence is a separate step.

    Consequences¶

    • To add a source, a developer adds one file and one test.
    • A source module that fails to import breaks the start of the agent. This is intended. A broken source must not stay hidden.
    • The sources are reviewed in code and typed. The registry check at import time catches wrong names, non-HTTPS URLs, and unknown strategies early.
    • Source configuration is not editable at run time. A change needs a code release. This is an accepted trade-off for a single maintainer.
    • OCR is limited to one provider at first. Users who turn it off cannot read scanned documents.
    • Tavily has a cost and a rate limit. The page cap limits the cost per call.
    • The DNS rebinding window stays open until the connection is pinned to the checked address.
    • A source that opts out of the address check removes the protection for that source. A reviewer must approve each opt-out.
    • Open point: the Tavily daily credit budget.
    • Open point: the retention rule for rejected documents.
    • Open point: the review of the Mistral data-retention terms.
    • Open point: the OCR model pin.

    Alternatives Considered¶

    • Local folder strategy - rejected as unsafe. A path from a source or from a user can reach files outside the intended folder. It adds a path-traversal risk for little value.
    • Per-source YAML configuration - rejected. The sources are few, reviewed in code, and typed. YAML brings back the registration layer that ADR-0014 removed, and it moves errors from import time to run time.
    • Class-level singleton registry - rejected. Hidden global state makes tests depend on each other. Module-level instances next to the base classes are simple, and tests can use a private Registry.
    • Inheritance for strategies - rejected. The strategies share no state, so a Protocol is enough.
    • Pin the connection to the checked address - not done now. It closes the DNS rebinding window, but it adds transport code that the project must maintain.
