# T2: unit tests for the close handler

## Context
T1 adds `_close_store` and a module-level `_store` in `src/tasks/fetch.py`. This task proves the handler behavior with no database and no network. It serves the success metrics: 0 `PostgreSQLStore()` calls with no store, 1 `close()` per store, and diff-cover >= 90%.

## Technical Approach
Create `tests/unit/tasks/test_fetch_close_store.py`.
- Autouse fixture: set `tasks.fetch._store = None` before and after each test.
- Patch `tasks.fetch.PostgreSQLStore` with a mock. Never open a connection.
- Six tests:
  1. No store: send handler, `PostgreSQLStore` mock not called.
  2. One store: `close` called once.
  3. `close` raises: warning logged with `exc_info` (use `caplog`), no exception, `_store` None.
  4. Cache cleared after close: `_make_store()` then handler, then `_make_store()` builds a new store.
  5. Failed build: `PostgreSQLStore` raises, `_store` stays None.
  6. Wiring: `_close_store` is connected to `worker_process_shutdown` (check by `worker_process_shutdown.send(sender=None)` calling it, or by receiver lookup).
- Check that `tests/unit/tasks/` has the package files the other unit tests use.

## Acceptance Criteria
```gherkin
Scenario: no store
  Given _store is None
  When _close_store runs
  Then the PostgreSQLStore mock has 0 calls

Scenario: one store
  Given _make_store built a mock store
  When _close_store runs
  Then store.close has 1 call

Scenario: close raises
  Given store.close raises RuntimeError
  When _close_store runs
  Then caplog has a WARNING record with exc_info and the call returns

Scenario: cache cleared
  Given _close_store ran after a store was built
  When _make_store is called again
  Then PostgreSQLStore has 2 calls and _store is the new store

Scenario: failed build
  Given PostgreSQLStore raises
  When _make_store is called
  Then the error propagates and _store is None

Scenario: signal wiring
  Given the module is imported
  When worker_process_shutdown.send runs with a store set
  Then store.close has 1 call
```
