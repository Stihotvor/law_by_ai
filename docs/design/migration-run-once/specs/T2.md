# T2: Advisory lock in migrations/env.py

## Context
Serves the goal: concurrent `alembic upgrade head` runs apply each migration once without "already exists" errors. Path 1 of `decision.md`: one file of product code changes.

## Technical Approach
Edit `run_migrations_online()` in `migrations/env.py`. Online mode only.
- Constant `MIGRATION_LOCK_KEY = 0x6C61775F6D6967` (literal, no `hashtext()`).
- In `with connectable.connect() as connection:` run `SELECT pg_advisory_lock(:key)` (session lock, never `pg_advisory_xact_lock`), then `connection.commit()` to end the autobegin transaction.
- Then `context.configure(connection=connection, target_metadata=...)` and `begin_transaction` / `run_migrations`.
- `try/finally`: roll back an open transaction, then `pg_advisory_unlock(:key)` and commit. Wrap the unlock in try/except that logs the error, so it cannot hide the original error.
- `run_migrations_offline()` stays unchanged: no lock.
- No timeout is set (unlimited wait is accepted).

## Acceptance Criteria
Scenario: Concurrent runs
  Given an empty scratch database
  When 2 `alembic upgrade head` processes run at once
  Then both exit 0 and `alembic_version` has 1 row equal to head

Scenario: Wait for a held key
  Given another session holds the key 0x6C61775F6D6967
  When `alembic upgrade head` starts
  Then it is still running after 2 s and exits 0 after the release

Scenario: Failed migration frees the lock
  Given a migration raises an error during a run
  When the run ends
  Then the original error is raised and no advisory lock remains in `pg_locks`

Scenario: Offline mode
  Given no database connection
  When `alembic upgrade <first revision> --sql` runs
  Then it prints SQL, exits 0 and opens no connection
