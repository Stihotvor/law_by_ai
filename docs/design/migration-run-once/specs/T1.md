# T1: Integration tests first (red)

## Context
Proves requirements "Success Metrics": concurrent upgrades apply once, a run blocks while the lock is held, and no lock stays after a run. Tests come before the fix, so the blocking test must fail before T2.

## Technical Approach
Create `tests/integration/test_migration_lock.py`, marked `integration`. Copy the scratch DB pattern of `test_old_volume_upgrade.py`: create `miglock_<hex>` with `factories.scratch_db.superuser_url()`, drop it with `WITH (FORCE)` in `finally`, skip only when the host is unreachable (`factories.db_probe.is_unreachable`). Run the owner URL (`get_settings().postgres_owner_url`) with the scratch database name.
- Do not import `migrations/env.py` (it runs migrations on import). Copy the literal `LOCK_KEY = 0x6C61775F6D6967` in the test.
- Concurrent test: start 2 `alembic upgrade head` subprocesses at once. Each subprocess runs `python -c` with `alembic.command.upgrade`, because the CLI cannot set `sqlalchemy.url` to the scratch database. It runs the same `env.py`.
- Blocking test: a session holds `pg_advisory_lock(LOCK_KEY)`, a subprocess upgrade starts, the test checks it still runs after 2 s, releases the lock, then waits for exit 0. A wrong key in env.py makes this test fail.
- No-lock test: upgrade to head, upgrade again, then query `pg_locks` for `locktype = 'advisory'` on the scratch database.
- Tests: `test_concurrent_upgrades_apply_once`, `test_upgrade_blocks_while_lock_held`, `test_no_lock_left_at_head`.

## Acceptance Criteria
Scenario: Concurrent upgrades apply once
  Given an empty scratch database
  When 2 `alembic upgrade head` processes start at the same time
  Then both exit with code 0
  And `alembic_version` holds exactly 1 row equal to head

Scenario: Upgrade blocks while the key is held
  Given a session holds `pg_advisory_lock(0x6C61775F6D6967)` on the scratch database
  When an `alembic upgrade head` process starts
  Then the process is still running after 2 s
  And after the session releases the lock the process exits with code 0

Scenario: No lock left at head
  Given a scratch database at head
  When `alembic upgrade head` runs again and exits
  Then `pg_locks` has no advisory lock row for that database

Scenario: Red before the fix
  Given `migrations/env.py` has no lock
  When the 3 tests run
  Then `test_upgrade_blocks_while_lock_held` fails
