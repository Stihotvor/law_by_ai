## Context
`migrations/env.py` must use the new module and the new setting. The online run then fails with a clear error when another session holds the key. It serves the requirements for the deadline, the start-time check and the offline case.

## Technical Approach
- In `migrations/env.py` keep `MIGRATION_LOCK_KEY`. Read `Settings().migration_lock_timeout_s` before `connect()`, in online mode only.
- Wrap the migration run with `advisory_lock(connection, MIGRATION_LOCK_KEY, timeout_s)` from `storage.advisory_lock`.
- Offline (`--sql`) takes no lock and reads no deadline.
- Extend `tests/integration/test_migration_lock.py`. Keep the 4 existing tests unchanged. Run Alembic in a subprocess.
- The new test holds the key on a second connection and records its `pg_backend_pid()`.
- Resolved: `env.py` already imports `config.settings` and `plugins.*` from `src/`, so `storage.*` imports the same way.

## Acceptance Criteria
Scenario: timeout with a held key
  Given a second connection holds key 0x6C61775F6D6967
  And `MIGRATION_LOCK_TIMEOUT_S` is 2
  When `alembic upgrade head` runs
  Then the run exits non-zero in 2 s to 5 s
  And the output contains "0x6C61775F6D6967"
  And the output contains the real backend pid of the holder
  And `alembic_version` has 0 changed rows

Scenario Outline: invalid deadline
  Given `MIGRATION_LOCK_TIMEOUT_S` is "<value>"
  When `alembic upgrade head` runs
  Then the run exits non-zero before it connects
  And the output contains "MIGRATION_LOCK_TIMEOUT_S"
  Examples:
    | value |
    | 0     |
    | -5    |
    | abc   |

Scenario: offline mode
  Given `MIGRATION_LOCK_TIMEOUT_S` is "abc"
  When `alembic upgrade head --sql` runs
  Then the run exits with code 0

Scenario: existing behaviour
  Given the 4 existing tests in `test_migration_lock.py`
  When they run
  Then all 4 pass unchanged
