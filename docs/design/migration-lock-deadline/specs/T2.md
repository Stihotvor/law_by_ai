## Context
The lock logic moves into a testable module with an injectable clock and sleep. It polls with a deadline and reports the holder. It serves the requirements for the poll, the timeout error and the unit-test success metric.

## Technical Approach
- Create `src/storage/advisory_lock.py` with context manager `advisory_lock(connection, key, timeout_s, *, clock=time.monotonic, sleep=time.sleep, poll_s=1.0)`.
- Define `AdvisoryLockTimeout(RuntimeError)` with `key`, `timeout_s`, `holder_pid: int | None`. The message has the key in hex, the deadline, and the pid or "unknown".
- Loop: run `pg_try_advisory_lock`, end the transaction after each try, log one wait line on the first failure, sleep `poll_s`, stop at the deadline.
- On the deadline, query `pg_locks` with the key split into `classid`/`objid` and `objsubid=1`. Then raise. The body never runs.
- A database error in a poll or in the `pg_locks` query propagates unchanged.
- Release logs a failure and does not raise.
- Tests in `tests/unit/test_advisory_lock.py` use a fake connection, clock and sleep.
- Resolved: use stdlib `logging.getLogger(__name__)`, as `plugins/relational_db/postgres.py` does.

## Acceptance Criteria
Scenario: free lock
  Given the first try returns true
  When the context is entered
  Then the body runs
  And no wait line is logged
  And sleep is never called

Scenario: lock freed before the deadline
  Given the first try returns false and the second returns true
  When the context is entered
  Then sleep is called once with 1.0
  And exactly one wait line is logged
  And the body runs

Scenario: deadline reached with a known holder
  Given every try returns false and the holder query returns pid 4242
  When the deadline passes
  Then `AdvisoryLockTimeout` is raised
  And the message contains "0x6C61775F6D6967", the deadline in seconds and "4242"
  And the body did not run

Scenario: deadline reached with an unknown holder
  Given every try returns false and the holder query returns no row
  When the deadline passes
  Then the message contains "unknown"
  And `holder_pid` is None

Scenario: database error in a poll or in the holder query
  Given the connection raises a database error in a poll
  When the context is entered
  Then the same error propagates
  And it is not an `AdvisoryLockTimeout`
  And the same holds for an error in the `pg_locks` query

Scenario: release failure
  Given the unlock call raises an error after the body
  When the context exits
  Then a failure is logged
  And no exception leaves the context
