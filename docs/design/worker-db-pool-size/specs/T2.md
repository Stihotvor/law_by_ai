# T2: PostgreSQLStore pool parameter

## Context
The store must take its pool from the caller so the worker can use 1 + 1 and the app keeps 5 + 10. It serves the goal of at most 4 worker connections and the failure mode that a bad value fails at engine build time. It depends on T1.

## Technical Approach
In `src/plugins/relational_db/postgres.py`:
- `PostgreSQLStore.__init__(on_document_deleted=None, *, pool: PoolConfig | None = None)`. Store `pool`. Do not read settings and do not raise for the pool.
- In `initialize()`, resolve the config first: `pool or get_settings().app_pool_config()`. Then call `create_engine(url, future=True, pool_size=cfg.size, max_overflow=cfg.max_overflow, pool_pre_ping=True, pool_timeout=30)`.
- Do not change `SchemaNotAtHeadError` behavior.

Tests in `tests/unit/plugins/test_postgres_pool.py`: patch `create_engine` or use a SQLite-free fake URL with a real `QueuePool`. Assert `engine.pool.size()` and `engine.pool._max_overflow`. Assert the `create_engine` call gets `pool_pre_ping=True` and `pool_timeout=30`.

## Acceptance Criteria
```gherkin
Scenario: Worker pool
  Given a store built with pool=PoolConfig(1, 1)
  When initialize() builds the engine
  Then pool.size() is 1 and the max overflow is 1

Scenario: Default app pool
  Given a store built without pool and no pool variables set
  When initialize() builds the engine
  Then pool.size() is 5 and the max overflow is 10

Scenario: Engine options
  Given any store
  When initialize() calls create_engine
  Then pool_pre_ping is True and pool_timeout is 30

Scenario: Bad app setting
  Given POSTGRES_POOL_SIZE is "0" and the store has no pool argument
  When initialize() is called
  Then ValueError naming POSTGRES_POOL_SIZE is raised and create_engine was not called

Scenario: Constructor does not read settings
  Given POSTGRES_POOL_SIZE is "0"
  When PostgreSQLStore() is constructed
  Then no error is raised
```
