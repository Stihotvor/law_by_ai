# T3: Worker store uses the worker pool

## Context
The Celery fetch task builds its store lazily in each prefork child. It must use the worker pool so the worker opens at most 4 connections with `--concurrency=2`. It depends on T2.

## Technical Approach
- `src/tasks/fetch.py`: `_make_store()` returns `PostgreSQLStore(pool=get_settings().worker_pool_config())`. The config is resolved before `initialize()`. On a `ValueError`, `_store` stays None.
- Unit test `tests/unit/tasks/test_fetch_store.py`: (a) bad `WORKER_POSTGRES_POOL_SIZE` makes `_make_store()` raise `ValueError` and `fetch._store` is still None, and a later call with a good value succeeds. (b) The fetch task gets its store only from `_make_store`: patch `_make_store` and assert the task calls it, and assert no other `PostgreSQLStore(` call exists in `src/tasks/fetch.py` (source check).
- Integration test `tests/integration/test_fetch_worker_pool.py`, function `test_fetch_document_worker_pool`. Follow `tests/integration/test_fetch_task_integration.py` and `conftest.py`: use `pytestmark = [pytest.mark.integration, pytest.mark.usefixtures("eager_celery")]`, the `postgres_url` fixture, the `registries` and `source_url` fixtures pattern (shared fakes from `fakes.fetch`), and reset `fetch._store` with monkeypatch. Set `WORKER_POSTGRES_POOL_SIZE=1` and `WORKER_POSTGRES_MAX_OVERFLOW=1`. Mock only the network edge (the fake source). Use the real store. Assert `fetch._store`'s engine `pool.size() == 1`, the max overflow is 1, and the stored row exists.
- Resolved: assert the pool through SQLAlchemy introspection: `pool.size() == 1`, max overflow 1, and `pool.checkedout() == 0` after the task. A `pg_stat_activity` count is not needed.

## Acceptance Criteria
```gherkin
Scenario: Worker store uses the worker pool
  Given WORKER_POSTGRES_POOL_SIZE is "1" and WORKER_POSTGRES_MAX_OVERFLOW is "1"
  When _make_store() is called
  Then the store receives PoolConfig(1, 1)

Scenario: Bad worker value
  Given WORKER_POSTGRES_POOL_SIZE is "0" and fetch._store is None
  When _make_store() is called
  Then ValueError naming WORKER_POSTGRES_POOL_SIZE is raised and fetch._store is still None

Scenario: Retry after a bad value
  Given a previous _make_store() call failed on a bad value
  When the value is fixed and _make_store() is called again
  Then it returns a store and fetch._store is set after the next task

Scenario: Only _make_store builds the store
  Given the source of src/tasks/fetch.py
  When it is searched for PostgreSQLStore( calls
  Then the only call is inside _make_store

Scenario: fetch_document with a 1 + 1 pool
  Given a live PostgreSQL, a fake source and a 1 + 1 worker pool
  When fetch_document runs in eager mode
  Then the document row is stored, the engine has pool.size() 1 and overflow 1, and at most 2 connections are open
```

- Tests exist for every scenario and pass.
- The quality gate reports pass or skipped (never fail).
