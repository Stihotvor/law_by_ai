# T2: Integration test, changed status server default gives exactly 1 modify_default

## Context
T1 turns the comparison on, but only the 0-diff test uses it. This test proves the comparison catches a real change. It serves the success metric "a changed model server default gives a non-empty diff".

## Technical Approach
- In `tests/integration/test_document_status_migration.py`, add `test_autogenerate_detects_changed_server_default`. It uses the `engine` fixture and `AUTOGEN_COMPARE_OPTS` from `data.autogen`.
- Copy ALL tables of `Base.metadata` into a fresh `MetaData` with `Table.to_metadata(copy_md)`. This avoids `remove_table` entries and missing FK targets.
- On the copy of `legal_document`, set `status.server_default` to a different value, for example `DefaultClause("approved")`.
- Run `compare_metadata(MigrationContext.configure(conn, opts=AUTOGEN_COMPARE_OPTS), copy_md)`.
- Alembic returns nested lists for column changes. Flatten the diff first, then keep the entries whose first item is `"modify_default"`.
- Assert exactly 1 such entry, for table `legal_document` and column `status`.
- Assert `Base.metadata` still has the original default (`'needs_review'`).

## Acceptance Criteria
```gherkin
Scenario: Changed server default is detected
  Given a scratch database at head
  And a copy of every Base.metadata table in a fresh MetaData
  And the copy of legal_document.status has a different server default
  When compare_metadata runs with opts=AUTOGEN_COMPARE_OPTS on the copy
  Then the flattened diff has exactly 1 modify_default entry
  And that entry names table legal_document and column status

Scenario: Original metadata is untouched
  Given the test above has run
  When the server default of Base.metadata legal_document.status is read
  Then it still equals needs_review
```
