# T8 New RLS integration tests

## Context
Each success metric and edge case in requirements.md needs a test that fails when the control breaks. This task adds one test file that covers them against a live PostgreSQL as `lawbyai_app`. It serves every success metric and every edge case.

## Technical Approach
- Create `tests/integration/test_rls_hardening.py`. Mark it `pytest.mark.integration`. Use `postgres_url` (app) and `owner_url` from `tests/integration/conftest.py` (T7).
- Setup: as the owner, in a tenant context (`app.current_tenant` set in each transaction), insert one user in tenant A with email `a@x.pl`, one in tenant B, and one inactive user. Use unique emails and tenant ids per test run. Delete them afterwards, per tenant.
- Use a different email in each tenant, because `uq_users_email` is global. The "2 tenants, 1 row" test checks that the lookup returns the single matching row.
- Assertions run as `lawbyai_app` with no tenant set unless stated.
- Metric queries: `pg_roles` for `current_user`; `pg_proc` for `prosecdef`, `proconfig`, `proowner::regrole`; `has_function_privilege('public', 'public.auth_lookup_user(text)', 'EXECUTE')`; `pg_class.relforcerowsecurity`.
- Edge cases: `auth_lookup_user(' A@x.PL ')`, `'%'`, `''`, unknown email, inactive user.
- Cross-tenant write: set `app.current_tenant` to A and INSERT a tenant B user. Expect `psycopg` `InsufficientPrivilege` or `DBAPIError` with the RLS message.
- `SET ROLE lawbyai_auth` as the app: expect an error.
- FORCE: `tenants` and `users` have FORCE on. `legal_document` and `rejected_document` have no FORCE and no RLS.

## Acceptance Criteria
```gherkin
Scenario: No tenant shows zero rows
  Given users and tenants rows exist for two tenants
  When lawbyai_app counts rows in users and tenants with no tenant set
  Then both counts are 0

Scenario: Lookup normalises the email
  Given a user a@x.pl in tenant A and another user with a different email in tenant B
  When lawbyai_app calls auth_lookup_user(' A@x.PL ') with no tenant set
  Then exactly 1 row returns and its tenant_id is A

Scenario Outline: Lookup returns nothing for bad input
  Given users exist
  When lawbyai_app calls auth_lookup_user('<email>')
  Then 0 rows return
  Examples:
    | email                 |
    | %                     |
    |                       |
    | nobody@unknown.example |

Scenario: Inactive user is returned
  Given a user with is_active = false
  When lawbyai_app calls auth_lookup_user with that email
  Then 1 row returns with is_active false

Scenario: App role has no bypass
  Given an app connection
  When SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user runs
  Then both are false

Scenario: Function definition
  Given the schema at head
  When pg_proc is read for auth_lookup_user
  Then prosecdef is true, proconfig has search_path, proowner is lawbyai_auth
  And has_function_privilege('public', 'public.auth_lookup_user(text)', 'EXECUTE') is false

Scenario: App cannot take the auth role
  Given an app connection
  When it runs SET ROLE lawbyai_auth
  Then PostgreSQL raises an error

Scenario: Tenant A cannot write tenant B
  Given app.current_tenant is A
  When lawbyai_app inserts a users row with tenant_id B
  Then the WITH CHECK fails

Scenario: FORCE RLS state at head
  Given the schema at head
  When relforcerowsecurity is read for tenants, users, legal_document, rejected_document
  Then it is true for tenants and users
  And it is false for legal_document and rejected_document
```
