# T1 Init script for three roles

## Context
Today one role is superuser and table owner, so RLS protects nothing. This task creates the three roles of the design on fresh volumes. It serves the Technical Constraints on roles and the success metric `rolsuper = false` and `rolbypassrls = false`.

## Technical Approach
- Create `docker/initdb/00-roles.sh`. The postgres image runs it once on an empty volume, as the bootstrap superuser (`POSTGRES_USER`).
- Use `psql -v ON_ERROR_STOP=1` with passwords passed as `-v` variables from env, never written in the file.
- Role names are fixed: `lawbyai_owner`, `lawbyai_app`, `lawbyai_auth`.
- `lawbyai_owner`: LOGIN, NOSUPERUSER, NOBYPASSRLS, no CREATEDB. `GRANT CREATE, USAGE ON SCHEMA public`. Database ownership is not required.
- `lawbyai_app`: LOGIN, NOSUPERUSER, NOBYPASSRLS, NOINHERIT, NOCREATEDB, NOCREATEROLE.
- `lawbyai_auth`: NOLOGIN, BYPASSRLS, NOINHERIT, NOCREATEDB, NOCREATEROLE. `GRANT USAGE ON SCHEMA public`.
- The init script only creates roles, memberships and schema grants. It does not grant column SELECT on `users`, because the table does not exist at init time. T4 grants it in the migration.
- `GRANT lawbyai_auth TO lawbyai_owner WITH INHERIT FALSE, SET TRUE`.
- Env variables: `POSTGRES_USER` and `POSTGRES_PASSWORD` stay the bootstrap superuser. Only the `postgres` service and the init script use them. Two new variables hold the login passwords: `LAWBYAI_OWNER_PASSWORD` and `LAWBYAI_APP_PASSWORD`.
- `docker/docker-compose.yml`, service `postgres` (line 59 `environment:`): pass the two new passwords and mount `./initdb:/docker-entrypoint-initdb.d:ro`. The service is `read_only: true` with `user: "70:70"`, so the script must be readable by uid 70 and executable or run through `sh`.
- `docker/.env.example`: add the two passwords with `change-me` values (the init program rejects `change-me` prefixes for secrets in `validate_config`).

## Acceptance Criteria
```gherkin
Scenario: Roles exist with the right attributes
  Given a fresh postgres volume and passwords in env
  When the container finishes its first start
  Then pg_roles shows lawbyai_owner, lawbyai_app and lawbyai_auth, all with rolsuper = false
  And rolbypassrls is true only for lawbyai_auth
  And rolcanlogin is false for lawbyai_auth
  And rolcreatedb is false for lawbyai_owner

Scenario: Owner can build and set the function owner
  Given the roles exist
  When the query reads pg_auth_members for lawbyai_auth
  Then lawbyai_owner is a member with inherit_option = false and set_option = true
  And has_schema_privilege('lawbyai_owner', 'public', 'CREATE') is true

Scenario: App cannot reach the privileged role
  Given the roles exist
  When lawbyai_app runs SET ROLE lawbyai_auth
  Then PostgreSQL raises an error

Scenario: No password in the repo
  Given the script file
  When a test greps docker/initdb/00-roles.sh for password literals
  Then it finds none
```
