# T4: PostgresProcedureRepository with concurrency and read tests

## Context
The SQL adapter implements the `ProcedureRepository` port against the T3 tables. It keeps an import atomic and keeps history. It serves the transaction, identical-content and revision rules in requirements.md.

## Technical Approach
In `src/plugins/relational_db/procedures.py` add `PostgresProcedureRepository(engine)`. It sits beside `PostgreSQLStore` and is not a method of it. Each call opens its own session. Reads return frozen pydantic objects, so no lazy load happens after the session closes.

`save(procedure, actor)` runs in one READ COMMITTED transaction, in this order:
1. `INSERT ... ON CONFLICT (slug) DO UPDATE SET slug = EXCLUDED.slug RETURNING id, revision`. This locks the row, also for a new slug.
2. Compare `procedure.model_dump(mode="json", exclude={"revision"})` with the `content` of the latest revision (jsonb equality). The actor does not count. If equal, roll back, return `changed=False`, and do not touch `updated_at`.
3. Delete the steps of the procedure and insert the new steps.
4. `UPDATE procedure SET revision = revision + 1`, then insert the revision row with the actor. The first import is revision 1.

`get(slug)` reads the procedure and its steps in one join statement. `list()` returns summaries sorted by slug. A `UNIQUE(procedure_id, revision)` IntegrityError and other database errors map to `ProcedureStoreError` with the cause chained and no content in the message.

Tests in `tests/integration/test_procedure_repository.py` run in the Docker suite and connect as `lawbyai_app`.

## Acceptance Criteria
Scenario: first save
  Given an empty database
  When `save` runs for slug "pesel"
  Then the result is revision 1 with `changed=True` and one revision row exists with the actor

Scenario: identical content
  Given "pesel" is saved
  When `save` runs again with equal content and another actor
  Then `changed=False`, the revision count is unchanged and `updated_at` is unchanged

Scenario: changed content
  Given "pesel" is saved at revision 1
  When `save` runs with one step text changed
  Then the result is revision 2 and `get("pesel")` returns the new steps only

Scenario: failed save keeps old data
  Given "pesel" is saved
  When a `save` fails in the middle, for example a step violates a CHECK
  Then `ProcedureStoreError` is raised and `get("pesel")` returns the old data at the old revision

Scenario: concurrent saves
  Given "pesel" exists
  When two threads save different content for it at the same time
  Then the revisions are distinct and consecutive, and the revision rows match the final state

Scenario: not found and empty
  Given an empty database
  When `get("nope")` and `list()` run
  Then `get` returns `None` and `list` returns an empty list

Scenario: read speed
  Given 3 saved procedures
  When `get` and `list` run
  Then each returns in under 100 ms

## Build notes (from T1)
- `Procedure.model_dump(mode="json")` holds `revision`. The identical-content compare and the stored `content` snapshot exclude `revision` (use `model_dump(mode="json", exclude={"revision"})`). `parse_procedure_yaml` rejects a `revision` key in YAML. The repository sets `revision` with `model_copy(update=...)` on read.
- Rebuilding a stored step skips the future-date check (no clock context).
- The first import inserts revision 1 (the CHECK needs revision >= 1). Each later import adds 1.
