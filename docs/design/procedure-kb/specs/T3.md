# T3: ORM tables, Alembic migration, grants and privilege tests

## Context
Procedures live in shared PostgreSQL tables with an append-only revision history. The database constraints are a second guard after pydantic. This task serves the table, history and grant rules in requirements.md.

## Technical Approach
- `src/data/models.py`: add ORM tables `procedure`, `procedure_step`, `procedure_revision` on the same `Base` that `migrations/env.py` reads. No `tenant_id`, no RLS. Every column NOT NULL.
- `migrations/versions/procedure_kb_tables.py`: one migration after head `c4a91e7f2b58`. Use frozen literal names. Run `SET LOCAL lock_timeout = '5s'` in upgrade and downgrade. The downgrade stops with an error when `procedure_revision` holds rows.
  - `procedure`: `id` BIGINT GENERATED ALWAYS AS IDENTITY, `slug` unique, `title`, `schema_version`, `revision`, `updated_at` timestamptz default now(). CHECKs: `slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'`, `btrim(title) <> ''`, `revision >= 1`, `schema_version >= 1`.
  - `procedure_step`: PK `(procedure_id, position)`. `procedure_id` FK ON DELETE CASCADE, `key`, `text`, `source_url`, `last_checked` DATE, `verify_with_office`. `UNIQUE(procedure_id, key)`. CHECKs: `position >= 0`, `key` kebab-case, non-empty text and verify line, `source_url LIKE 'https://%'`.
  - `procedure_revision`: `id` identity, `procedure_id` FK ON DELETE RESTRICT, `revision >= 1`, `content` JSONB with CHECK `jsonb_typeof(content) = 'object'`, `actor` non-empty, `created_at` timestamptz default now(), `UNIQUE(procedure_id, revision)`.
  - Grants to `lawbyai_app`, explicit, TRUNCATE revoked: `procedure` SELECT, INSERT, UPDATE. `procedure_step` SELECT, INSERT, UPDATE, DELETE. `procedure_revision` SELECT, INSERT.
- Tests in `tests/integration/test_procedure_schema.py`. Run them in the Docker suite on PostgreSQL 18. Connect as the owner role for the DDL and CHECK tests, and as `lawbyai_app` for the privilege tests.
- The "date not in the future" rule stays in pydantic only.

## Acceptance Criteria
Scenario: migration round trip
  Given a database at head `c4a91e7f2b58`
  When `alembic upgrade head` then `alembic downgrade -1` run with no revision rows
  Then the three tables exist after upgrade and none exist after downgrade

Scenario: CHECK constraints reject bad rows
  Given the migrated schema
  When a test inserts a bad slug, an empty title, `revision` 0, `source_url` "http://x", an empty step text, a non-object `content`, or an empty `actor`
  Then each insert fails with a check violation

Scenario: app role cannot change history
  Given a connection as `lawbyai_app` and one revision row
  When it runs UPDATE or DELETE on `procedure_revision`, DELETE on `procedure`, or TRUNCATE on any of the three tables
  Then each statement fails with permission denied

Scenario: app role can do its writes
  Given a connection as `lawbyai_app`
  When it inserts and updates `procedure`, and inserts, updates and deletes `procedure_step`, and inserts `procedure_revision`
  Then each statement succeeds

Scenario: revision rows block procedure delete
  Given a procedure with a revision row
  When the owner role deletes the procedure
  Then the delete fails with a foreign key violation

Scenario: downgrade guards history
  Given `procedure_revision` holds one row
  When `alembic downgrade -1` runs
  Then it stops with an error and the tables remain
