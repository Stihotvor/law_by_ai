## Context
The store must not let a caller change `status` through `save_document` or `update_document`. T1 gives `apply_update` an allowlist and dropped key names. This task uses them in the store and logs one warning per call. It serves the requirements for insert, upsert and update behavior and for 0 new migrations.

## Technical Approach
- In `src/plugins/relational_db/postgres.py`, `save_document` inserts with `status = DocumentStatus.NEEDS_REVIEW.value` as a constant. `tenant_id` is read as today (parameter, payload, context).
- Log one warning per call, with dropped key names only, never values. The upsert branch and `update_document` use the names returned by `apply_update`. The insert branch warns when the payload has a `status` key.
- `save_document` still writes a generated `id` back into the caller's dict. Nothing else changes in the dict.
- Remove `validate_status` and its import from `src/plugins/relational_db/postgres.py` and `src/plugins/relational_db/mappers.py`. Remove the unused `DocumentStatus` import from `mappers.py`. `postgres.py` keeps `DocumentStatus`.
- Unknown status values no longer raise `ValueError`. They are dropped with the warning.
- Add integration tests in `tests/integration/plugins/test_postgres_status_guard.py`. Use the real store and a caplog check on the warning.
- Add no migration.

## Acceptance Criteria
Scenario: update cannot change status
  Given a stored document with status "needs_review"
  When `update_document(doc_id, {"status": "approved", "title": "x"})` runs
  Then the stored status equals "needs_review"
  And the stored title equals "x"

Scenario: insert ignores status
  Given no stored document with the payload id
  When `save_document` runs with a new payload with status "approved"
  Then the stored status equals "needs_review"
  And one warning names the key "status" and not the value "approved"

Scenario: insert without status
  Given a new payload with no status key
  When `save_document` runs
  Then the stored status equals "needs_review"
  And no status warning is logged

Scenario Outline: upsert keeps the stored status
  Given a stored document with status "approved"
  When `save_document` runs with the same id and status "<value>"
  Then the stored status equals "approved"
  Examples:
    | value        |
    | needs_review |
    | approved     |

Scenario Outline: unknown status does not raise
  Given a stored document with status "needs_review"
  When `update_document(doc_id, {"status": <value>})` runs
  Then no error is raised
  And the stored status equals "needs_review"
  Examples:
    | value      |
    | "bogus"    |
    | "rejected" |
    | ""         |
    | None       |

Scenario: warning names keys and not values
  Given a stored document
  When `update_document(doc_id, {"status": "approved-secret", "foo": 1})` runs
  Then exactly one warning is logged for the call
  And the warning contains "status" and "foo"
  And the warning does not contain "approved-secret"

Scenario: reads still return status
  Given a stored document with status "needs_review"
  When `get_document(doc_id)` runs
  Then the result has status "needs_review"

Scenario: validate_status is gone and no migration is added
  Given the change is applied
  When `grep -rn validate_status src` runs
  Then the output is empty
  And `migrations/versions` has no new file
