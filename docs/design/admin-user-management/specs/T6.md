# T6: Service integration tests on real Postgres

## Context
Unit tests use a fake port. These tests use the real store, the real service and real Postgres. They prove the end-to-end test from the requirements and the security metrics.

## Technical Approach
In `tests/integration/test_user_service.py`, wire `PostgreSQLStore` into the service. Set the tenant context and principal as login does. Verify login with the existing credential lookup and `session_version` check used by `auth.py`. Time each action with `time.perf_counter`. Mock only the network edge.

## Acceptance Criteria
```gherkin
Scenario: Created user logs in
  Given an admin of tenant A
  When the admin creates a user and that user logs in with the typed password
  Then the login succeeds and the user belongs to tenant A

Scenario: Deactivated user is refused
  Given a logged-in user with a cookie
  When the admin deactivates that user
  Then a new login fails
  And the old cookie fails because session_version differs

Scenario: Privilege escalation
  Given an admin of tenant A
  When the admin creates a user with a role outside VALID_ROLES
  Then UserCreateRefusedError is raised and no row exists

Scenario: Role user
  Given a principal with role "user"
  When create_user and deactivate_user are called
  Then 0 calls succeed and no row changes

Scenario: Speed
  Given local Postgres
  When create_user and deactivate_user run
  Then each call takes less than 1 second
```

## Definition of Done
- The task's `done_when` check passes: pytest tests/integration/test_user_service.py passes.
- Tests exist for every scenario and pass.
- The quality gate reports pass or skipped (never fail). The Docker suite may be CI-only in a worktree.
- No `OPEN:` item remains.
