# T4: User service

## Context
The service holds all business rules: principal binding, validation, hashing, audit. It uses only the port, so unit tests use a fake. It serves the role, password, email and audit requirements.

## Technical Approach
- `src/core/security/passwords.py`: move the password limit constants (12 characters minimum, 72 UTF-8 bytes maximum) here from `src/bootstrap/init_stack.py`. `init_stack.py` imports them from the new place.
- `src/core/users/service.py`, every call, in order: raise `PrincipalRequiredError` if `get_current_tenant()` is empty. Call `require_admin_principal()`. Call `port.find_active_admin(normalise_email(principal.email))`. If it returns `None`, raise `PrincipalRequiredError`. The returned `id` is the actor id.
- `create_user(email, password, role, name)`: trim and lowercase email. Require one `@`, at most 256 characters, not blank. Name at most 256. Role by `valid_role`. Password limits as above. Every failure raises `UserCreateRefusedError`. Run `hash_password` before the insert. Call `port.insert_user(email=..., password_hash=..., role=..., name=...)` and return its `UserRecord`.
- `deactivate_user(user_id)`: call `port.deactivate_user(user_id, actor_id=actor["id"])`. The port raises `UserNotFoundError`, `SelfDeactivationError` or `LastAdminError`. The service lets them propagate. Emit a stdlib logging audit event with actor id, target id, action and the returned `changed` flag. Never log the password or the hash.
- `list_users()`: call `port.list_users()` and return the `UserRecord` list. It has no hash.
- The tenant is never an argument.
- The port signatures are in the "Port signatures" section of `decision.md`. The fake port in the unit tests implements the same four methods.

## Acceptance Criteria
```gherkin
Scenario: Role user is refused
  Given a principal with role "user"
  When create_user or deactivate_user is called
  Then the call raises and the fake port records 0 writes

Scenario: Empty tenant
  Given no current tenant
  When any service call runs
  Then PrincipalRequiredError is raised before the port is called

Scenario: Actor is not an active admin
  Given find_active_admin returns None
  When a service call runs
  Then PrincipalRequiredError is raised

Scenario: Invalid input
  Given a bad role, a blank email, an email without "@", or a password of 11 characters or 73 bytes
  When create_user runs
  Then UserCreateRefusedError is raised and the port insert is not called

Scenario: Email is normalised
  Given email "  A@X.PL "
  When create_user succeeds
  Then the port receives "a@x.pl" and a bcrypt hash, not the password

Scenario: Actor id goes to the port
  Given find_active_admin returns a row with id "A1"
  When deactivate_user runs on "U2"
  Then the fake port receives user_id "U2" and actor_id "A1"

Scenario: Logs and audit
  Given a successful create and a successful deactivate
  When the captured logs are read
  Then neither the password nor the hash appears
  And an audit event holds actor id, target id and action
```
