# T3: PostgreSQLStore.deactivate_user

## Context
An admin must deactivate users without removing the last admin, even under concurrency. The existing trigger bumps `session_version`, which invalidates the old cookie. It serves the deactivate goal and the concurrency edge case.

## Technical Approach
In `src/plugins/relational_db/postgres.py`, add `deactivate_user(self, user_id: str, *, actor_id: str) -> bool`. The service passes `actor_id`, which is the `id` of the row that `find_active_admin` returned.
1. Tenant from `get_current_tenant()`. Empty raises `PrincipalRequiredError` before SQL.
2. Read the target under RLS with a `tenant_id` predicate. A missing or foreign id raises `UserNotFoundError`.
3. If `user_id == actor_id`, raise `SelfDeactivationError`. This runs inside the transaction, before the last-admin check.
4. If the target is an admin, first lock the tenant's active admin rows with `FOR UPDATE ORDER BY id`. No `LIMIT`, no `SKIP LOCKED`, nothing else locked before. If the locked set has one row or fewer, raise `LastAdminError`.
5. If the target has role `user`, lock only the target.
6. `UPDATE users SET is_active = false WHERE id = :id AND is_active RETURNING id`. Return `True` for one row. Return `False` for zero rows (idempotent no-op).
- One transaction. Roll back on error.
- Import the domain errors from `core.users.errors` and `PrincipalRequiredError` from `core.security`.
- Tests in `tests/integration/test_store_deactivate.py`.

## Acceptance Criteria
```gherkin
Scenario: Foreign or unknown id
  Given a user in tenant B
  When tenant A admin deactivates that id, or a random id
  Then UserNotFoundError is raised and the row is unchanged

Scenario: Already inactive target
  Given an inactive user with session_version N
  When deactivate_user runs on it
  Then no error is raised, it returns False, and session_version is still N

Scenario: Old cookie fails
  Given an active user with session_version N
  When an admin deactivates that user
  Then it returns True, is_active is false and session_version is not N

Scenario: Self and last admin
  Given a tenant with one active admin
  When that admin deactivates self
  Then SelfDeactivationError is raised
  And when another admin is the sole active admin, deactivating that admin raises LastAdminError

Scenario: Two sessions race
  Given a tenant with exactly two active admins
  When each admin deactivates the other in two concurrent sessions
  Then exactly one active admin remains

Scenario: No tenant set
  Given no current tenant
  When deactivate_user runs
  Then PrincipalRequiredError is raised and 0 rows change
```
