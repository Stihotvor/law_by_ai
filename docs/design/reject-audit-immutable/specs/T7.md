# T7: Privilege, schema-guard and migration round-trip integration tests

## Context
The revision from T2 must really deny the app role, and a later migration must not restore the rights by accident. This task proves both. It serves the success metrics 3 of 3 denied, 2 of 2 allowed, and the upgrade-downgrade-upgrade round trip.

## Technical Approach
Create `tests/integration/test_rejected_document_privileges.py`, marked `integration`, skipped when PostgreSQL is unreachable (as `tests/integration/test_reject_document.py:1-22` does, with `can_connect`).
- App engine: `get_settings().postgres_url`. Owner engine: `postgres_owner_url`.
- Privileges: run each statement in its own transaction as `lawbyai_app`. UPDATE, DELETE and TRUNCATE each raise `ProgrammingError` whose `orig.sqlstate` (or `pgcode`) is `42501`. INSERT and SELECT succeed. Clean test rows as the owner.
- Schema guard on the head schema: `has_table_privilege` false for UPDATE, DELETE and TRUNCATE. `has_any_column_privilege(..., 'UPDATE')` false. PUBLIC has no rights (query `information_schema.role_table_grants` or `aclexplode` for grantee 0).
- Round trip as the owner: run alembic upgrade head, downgrade -1, upgrade head, using the project's Alembic config (`alembic.ini`, `docs/migrations.md`). After the downgrade UPDATE and DELETE are true and TRUNCATE is false. Always restore head in a `finally`.
- Resolved: reuse the Alembic `command.upgrade` / `command.downgrade` pattern of `tests/integration/test_rls_hardening.py` and `tests/integration/test_document_status_migration.py`, run with the owner URL.

## Acceptance Criteria
```gherkin
Scenario Outline: app role is denied
  Given the head schema
  When lawbyai_app runs <statement> on rejected_document in its own transaction
  Then PostgreSQL raises SQLSTATE 42501
  Examples:
    | statement |
    | UPDATE    |
    | DELETE    |
    | TRUNCATE  |

Scenario: app role keeps insert and select
  Given the head schema
  When lawbyai_app runs INSERT and then SELECT on rejected_document
  Then both succeed

Scenario: schema guard
  Given the head schema
  When has_table_privilege and has_any_column_privilege are checked for lawbyai_app
  Then UPDATE, DELETE and TRUNCATE are false
  And PUBLIC has no privilege on the table

Scenario: migration round trip
  Given the owner connection
  When the schema goes upgrade, downgrade, upgrade
  Then every step passes
  And after the downgrade UPDATE and DELETE are true and TRUNCATE is false
  And the schema is back at head at the end
```
