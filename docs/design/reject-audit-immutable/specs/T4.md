# T4: Auth layer sets and resets the principal

## Context
The store reads the principal from the context. The UI auth layer must set it on every rerun and clear it on sign-out, so no stale actor stays. This serves the stale-actor failure mode.

## Technical Approach
Edit `src/ui/components/auth.py`.
- Import `RequestPrincipal`, `set_principal`, `reset_principal` from `core.security.principal`, next to the tenant import at line 22.
- `require_auth` (line 240): after `set_current_tenant(user["tenant_id"])` (line 251), call `set_principal(RequestPrincipal(user["email"], user["role"]))`.
- `_sign_out` (line 224): call `reset_principal()` after `reset_current_tenant()` (line 229).
- `logout_button` (line 273): call `reset_principal()` after `reset_current_tenant()` (line 286).
- Tests in `tests/unit/ui/test_auth_principal.py`. Reuse the Streamlit stubbing style of the existing auth unit tests (check the neighbours in `tests/unit/ui/`).
- `require_admin` (line 302) is unchanged.

## Acceptance Criteria
```gherkin
Scenario: require_auth sets the principal
  Given a valid session for an admin with email "a@x.pl"
  When require_auth returns
  Then get_principal() equals RequestPrincipal("a@x.pl", "admin")

Scenario: sign-out clears the principal
  Given a principal is set
  When _sign_out runs (st.stop is stubbed)
  Then get_principal() is None

Scenario: logout button clears the principal
  Given a principal is set and the Log out button is clicked
  When logout_button runs
  Then get_principal() is None before st.rerun is called
```
