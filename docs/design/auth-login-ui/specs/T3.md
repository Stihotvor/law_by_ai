# T3: UI escalation tests and require_admin_principal fail-open test

## Context
No test proves that a demoted or deactivated admin loses admin pages in an open session. `require_admin_principal` in `principal.py` is a third admin check with no fail-open test. Serves the Success Metrics (at least 3 UI escalation tests) and the Edge Cases of requirements.md.

## Technical Approach
Add tests only. Change no production code.

`tests/unit/ui/test_auth_escalation.py` (reuse the existing auth test fixtures and stubs in `tests/unit/ui/` if present):
- Per decision.md, each demotion or deactivation test runs `require_auth()` with `_lookup` stubbed to return the changed row, then `require_admin()`. Do not edit only `st.session_state["user"]`.
- Set up a valid session (`USERNAME_KEY` = `"<email>|<version>"`, future `EXPIRES_KEY`), first lookup returns an admin row and `require_admin()` passes. Then the stub returns the changed row and the next `require_auth()` plus `require_admin()` runs.
- Test names must match the `-k` filter: `test_demoted_admin_...`, `test_deactivated_admin_...`, `test_user_on_admin_page_...`, `test_current_role_...`.
- demoted: row role `"user"`. After `require_auth()`, `require_admin()` calls `st.warning("Admin role required.")` and `st.stop()`. A stop sentinel exception from the `st.stop` stub is acceptable.
- deactivated: row `is_active=False`. `require_auth()` signs out and stops. The session user key is cleared and no admin access remains.
- user on admin page: a user row from the start. `require_admin()` warns and stops.
- `current_role()` fail closed: `""` for no user, non-dict user, missing role, `None` role, non-string role. Upper case `"ADMIN"` returns `"ADMIN"` and `require_admin()` still stops (rbac is exact match).

`tests/unit/core/security/test_principal.py` (add to the file, or create it if absent):
- `require_admin_principal` raises `PrincipalRequiredError` when no principal is set, role is `"user"`, role is `"ADMIN"` or `""`, or the email is blank or whitespace.
- It returns the principal with the email stripped for an admin.

Manual mutation in review: remove each guard (`is_admin` check in `require_admin`, the `_usable` check in `_session_user`, the role check in `require_admin_principal`) and confirm the matching test fails.

## Acceptance Criteria
```gherkin
Scenario: demoted admin loses admin pages
  Given an open session of an admin and a login lookup that now returns role "user"
  When require_auth() and then require_admin() run
  Then st.warning is called with "Admin role required." and st.stop is called

Scenario: deactivated admin is signed out
  Given an open session of an admin and a login lookup that now returns is_active False
  When require_auth() runs
  Then the session user key is cleared and the page stops before any admin code

Scenario: user on an admin page
  Given a signed-in user with role "user"
  When require_admin() runs
  Then st.warning is called with "Admin role required." and st.stop is called

Scenario: current_role fails closed
  Given a session user that is missing, not a dict, or has a None, empty or non-string role
  When current_role() runs
  Then it returns ""

Scenario: require_admin_principal fails closed
  Given no principal, a "user" principal, an "ADMIN" principal, or an admin with a blank email
  When require_admin_principal() runs
  Then it raises PrincipalRequiredError

Scenario: require_admin_principal accepts an admin
  Given an admin principal with email " a@x.pl "
  When require_admin_principal() runs
  Then it returns a principal with email "a@x.pl" and role "admin"
```
